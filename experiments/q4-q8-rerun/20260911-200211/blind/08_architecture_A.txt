We design a payment worker that uses a simple idempotent job model in PostgreSQL and lets many workers run concurrently. The key points are: the **database state** is modeled with one row per job containing `idempotency_key` and `status` (`pending`/`processing`/`succeeded`/`failed`). The unique `idempotency_key` is **generated at job creation time** (based on the job id) and stored in the row. Each worker, when it receives a job, starts by updating the row status to `processing` in a **single statement**. Workers are then allowed to run concurrently; no locking is needed for state because the status check is performed via a unique `idempotency_key` index. The worker sends the same `idempotency_key` to the payment provider. The provider returns a confirmation for each unique key; if the same key is sent again, the provider ignores the duplicate charge. The worker records the provider’s success back in the database by issuing its own UPDATE after the provider responds. If a worker crashes after the provider accepted the charge but before the DB UPDATE, the job still appears as `processing` in the DB (the provider never wrote to the DB). A second worker that picks up the job will also see status `processing`; because the `idempotency_key` already exists in the row, the worker’s own update from the previous worker will already have set the status to `succeeded`—the job will be processed only once. **The system cannot guarantee exactly‑once execution**; the only guarantee is that no charge is duplicated, but due to the possible race between the provider call and the DB write, the same job could be processed twice if the worker crashes before the DB update and a second worker wins the race. However, with the idempotent key and a unique‑key check, the provider ensures at most one charge is made, so the business rule (no double charge) is met, but strict exactly‑once job processing is not. In practice, you accept this trade‑off: the provider’s idempotency makes the payment safe, while the database ensures no duplicate processing of the job.
