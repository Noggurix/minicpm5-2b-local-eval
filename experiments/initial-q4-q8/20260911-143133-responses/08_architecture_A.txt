We design the payment worker as a simple Go/Python worker that uses PostgreSQL only and relies on an idempotency key stored in a table.

**Database state model**

Create a single table `jobs`:

```sql
CREATE TABLE jobs (
    id              BIGINT PRIMARY KEY,
    idempotency_key TEXT NOT NULL,
    status         TEXT NOT NULL CHECK (status IN ('pending','queued','provider_charged','provider_failed','completed','retried')),
    attempt_count  INTEGER NOT NULL DEFAULT 0,
    provider_id    TEXT,          -- provider external ID (not used for the charge itself)
    locked_at      TIMESTAMPTZ,
    locked_by      TEXT          -- which worker locked the row
);
```

A row represents a job for a specific idempotency key. The key is **unique per job** (stored by the provider when it creates the job) and is the *only* data the worker ever sees. The `status` field tracks progress: `pending` → `queued` → `provider_charged` → `completed` (after PostgreSQL writes). The `attempt_count` lets us cap retries without infinite loops.

**Concurrency control**

Two workers can read the same `pending` row before any writes happen. We therefore use a **single‑row lock** obtained at the start of processing, using PostgreSQL’s `SELECT … FOR UPDATE` (exclusive row lock). Because the lock is on the entire row, only one worker can hold it at a time. Once a worker acquires the lock, it must:

1. Insert a new row (if the job does not exist yet) – this auto‑generates the idempotency key.
2. Write the row to the provider **once** and then copy the provider‑side idempotency key into the job table before flipping `status` to `provider_charged`.
3. Retry up to `max_attempts` with exponential back‑off; the same `attempt_count` guarantees the provider is only charged on the first successful call.
4. Write the final `completed` status (or `failed`).

Because the lock is acquired **inside a transaction**, the worker is a *serialised* worker per job, even though many rows can be processed concurrently. The provider is external; the worker never holds a lock on the provider.

**Idempotency key source**

The idempotency key originates from the payment provider when it creates the job (or is supplied by the provider client). The worker stores that key in the `idempotency_key` column, never altering it. When a worker calls the provider, it sends this key as part of the charge request; the provider uses it to guarantee that repeated requests with the same key do not produce duplicate charges.
