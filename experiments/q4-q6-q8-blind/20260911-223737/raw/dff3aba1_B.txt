We'll model state, concurrency, idempotency, crash recovery, and exact-once.

## Database state model
Store each job in a `jobs` table with columns: `job_id` (PK), `state` (integer: 0=pending, 1=processing, 2=success, 3=failed), `processed_at` timestamp, and `idempotency_key` (the key from the provider, if known). Workers only process a job when `state = 0` (or occasionally from 3).

## Concurrency control
To allow multiple workers but ensure only one processes a given job, use an exclusive row lock. On receipt, the worker executes a `SELECT ... FOR UPDATE` on the job row and transitions it to state 1 (`processing`). Other workers then see `state != 0` and skip. Rows are locked until the transaction commits, which includes the payment provider call.

## Idempotency key source
The key comes from the payment provider. Each job record includes an `idempotency_key`. Before calling the provider, the worker sends the job details (or the key) and the provider charges the customer, returning a confirmation. If the charge succeeds again (duplicate), the provider may return the same key (or an error), but the worker records the key in the database to know it was already used.

## Crash scenario
If a worker crashes after the provider accepts the charge but before PostgreSQL records the success, the job state is still `processing` (or `failed`). When another worker picks it up, they may retry. To avoid double charge, the worker should **not** retry a charge if the provider returned an idempotency key already recorded in the job row. But because the database transaction might have been split across crashes, we rely on the provider's idempotency behavior: calling the provider again with the same key will typically return the same result (success) without charging again. So the worker can simply resend the job; the provider handles duplicates.

## Exact-once execution?
**No.** The system can't guarantee exactly-once execution because of worker crashes and unsplittable transactions. However, we can guarantee *at-least-once* with idempotent processing and provider idempotency. If the job is reprocessed after initial success, the provider's idempotency key prevents double charges, but the job may still be processed multiple times. The database state ensures only one worker transitions to success, but crashes can leave the job in `processing`, leading to a double attempt. The system's claim should be *idempotent at-least-once* processing, not exactly-once.
