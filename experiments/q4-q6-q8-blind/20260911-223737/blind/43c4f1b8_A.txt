The design uses a PostgreSQL `jobs` table to model state. Each job has an `id`, a `status` (pending, processing, completed, failed), an `idempotency_key` (unique per job), and optional `provider_id`, `amount`, etc. Only one row per idempotency key exists, ensuring at-least-once delivery.

**Database modeling**
- Table `jobs`: `id` (PK), `status` (pg_safe_state), `idempotency_key` (UNIQUE), `created_at`, `completed_at`, `provider_id`, `amount`, `failure_reason`.
- A job is created with status `pending`, a worker processes it, then it moves to `completed` or `failed`. Retrying a failed job is allowed because the key remains unique.

**Concurrency control**
- Use row-level locking or a serializable advisory lock to allow only one worker to modify a job’s status at a time. In PostgreSQL, this can be enforced by an `UPDATE … SET status = 'completed' WHERE status = 'pending' AND idempotency_key = ? FOR UPDATE`. A unique index on `idempotency_key` prevents two workers from processing the same job concurrently. If a worker crashes after the payment provider accepts the charge but before the DB records success, the job is still marked `pending` (or `failed` if an error occurred). The provider might have been charged, but our system records nothing. Retrying later will attempt to process the same job. Because the `idempotency_key` is unique, the second worker will find the job’s status different from `pending` (it might be `processing` or `completed`). If the first worker failed partway, the job stays `pending` and a later worker can pick it up. 

**Idempotency key source**
The key is generated by the worker at job creation time (e.g., a UUID v4) and stored in the `jobs` table as a unique constraint. The same key is passed to the payment provider, ensuring that if the provider receives the same key twice, it only charges once.
