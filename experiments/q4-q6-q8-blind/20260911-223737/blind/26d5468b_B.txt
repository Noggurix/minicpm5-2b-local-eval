**Database state modeling:**  
A `jobs` table with columns `id`, `status` (pending/processing/completed/failed), and `idempotency_key`. Workers reference the same key for retries.

**Concurrency control:**  
Workers fetch a job row with `SELECT ... FOR UPDATE` (or similar) to avoid double-processing. Since retries are allowed, each worker must re-fetch after a provider call returns “already processed.”

**Idempotency key source:**  
The key is generated by the worker from the job `id` (or a unique UUID) and sent to the payment provider. The provider uses it to ensure a charge is made at most once per key.

**Crash between provider success and PG record:**  
If a worker crashes after the provider accepts the charge but before PG records success, the provider already performed the charge. A later worker will retry the job. It sends the same idempotency key; the provider will return the existing result (no second charge), and the worker updates the job status in PG.
