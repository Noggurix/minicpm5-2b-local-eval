**Database model**

Create a table `jobs` with columns:
- `id` (UUID, primary key)
- `idempotency_key` (string, unique per payment request)
- `status` (`pending` | `processing` | `completed` | `failed`)

Each row represents one payment job. When a worker starts a job, it first SELECTs the row with `FOR UPDATE` (or a similar exclusive lock) and sets `status = 'processing'`. When the worker finishes (or aborts), it rolls back and re‑selects the row. The provider’s idempotency key is stored with the job; the provider never charges the same key twice, so the worker never needs to check it.

**How workers handle concurrency**

The job is processed sequentially: a worker obtains an exclusive lock on the job row (`SELECT … FOR UPDATE`). This guarantees that two workers cannot both see the same locked row unless one has already released the lock, so at most one worker ever holds a job in `processing`. The database row itself is the sole coordination point; no application‑level queues are required.

**Idempotency key**

The idempotency key is supplied by the job definition (e.g., the request ID from the customer). The worker passes this key to the external payment provider. The provider, by contract, will charge the customer only once for that key. The worker does **not** store the key in the database; it is only used when the provider returns a confirmation. If the provider rejects a charge for an already‑charged key, the worker must mark the job as `failed` and re‑queue it, never double‑charging.

**What if a worker crashes after the provider accepts the charge but before PostgreSQL records success?**

The scenario:
1. Worker sends a request with idempotency key `k` to provider.
2. Provider returns a successful charge ID.
3. Worker updates the job status to `completed` and commits.
4. Worker crashes before the commit is flushed to PostgreSQL (i.e., the DB hasn't yet recorded the status change).
5. Another worker (or the same worker in a later run) picks up the same job.

Because the provider is idempotent, the provider will only charge once for key `k`. However, if another worker also charges, there will be two provider calls for the same key, potentially leading to a double‑charge if the provider rejects the second one. The system must guarantee that a job is never processed twice. To achieve this, we rely on PostgreSQL’s **REPEATABLE READ** commit isolation and the **idempotency key** itself. - Failed jobs are re‑queued only after a clean failure, never after a successful charge.
