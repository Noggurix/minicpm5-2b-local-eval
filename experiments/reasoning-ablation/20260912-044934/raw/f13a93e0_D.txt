**Database State:** Model jobs as a single row in a `jobs` table with columns `id`, `status` (pending/succeeded/failed), and `provider_response` (text). This avoids global locks.

**Concurrency Control:** Use PostgreSQL row-level locking. When a worker picks a job, it acquires a lock on the row. Other workers see the row as "held" and cannot proceed until the lock is released.

**Idempotency Key:** The key is generated by the worker itself from the job's unique ID. This ensures consistency if multiple workers fetch the same job.

**Crash Recovery:** If a worker crashes after the payment provider accepts the charge but before PostgreSQL records success, the next worker fetching the same job will see a "pending" status. It will re-attempt the payment. Because the provider supports idempotency keys, the provider will reject duplicate charges for the same key.

**Exactly-Once:** The system claims exactly-once execution. The database status acts as the checkpoint: a job cannot be "succeeded" twice. Retrying a failed job only re-fetches it; if already succeeded, it is skipped. Therefore, no charge is double-funded.
